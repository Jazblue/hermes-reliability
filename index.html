Hermes Reliability Desk

A practical reference for starting Hermes, diagnosing gateway and cron failures, and recording what actually fixed them.

Manual logs · Evidence-first fixes

Start here after a Windows restart

  1. Run hermes gateway status and record the reported state, PID and heartbeat.
  2. Run hermes cron status to inspect scheduler health.
  3. For a particular job, run hermes cron runs JOB_ID and check its newest execution.
  4. Compare status with the output file, Git state and remote commit where relevant.
  5. Change one thing at a time and verify the result before continuing.
Safety rule: a notification, valid JSON, or “completed” status alone does not prove every side effect succeeded. Verify the actual artifact separately.

29 October 2026 · Hermes, Tech Reddit Radar & integrations

Several small failures are adding up

Today’s troubleshooting showed that the Radar job can look stuck for a long time and then report completion. The local repository was clean and matched its remote at the time checked, but that alone did not prove the live page or every story was fresh.

  • Tech Reddit Radar / MCP: an extra setup step identified was interactive MCP server login/reauthorisation using hermes mcp login <server>, followed by a gateway reload. A scheduled background job cannot complete a browser OAuth consent flow on its own. The exact server and whether reauthorisation resolves the Radar issue still need verification.
  • Telegram and WhatsApp: Telegram status previously indicated WhatsApp was enabled but not paired. WhatsApp is reported not working today; this log records the symptom, not a confirmed root cause or repair.
  • Agent execution and code quality: logs showed repeated execute_code attempts without progress, malformed tool calls, and a Radar search returning “No results found”. These can cause poor results even when a model itself is capable.
  • Model/API reliability: Gemini was reported unhealthy due to a payment/credit error. The Free LLM API or selected models could contribute to inconsistent output, but the evidence so far does not prove that model quality is the single cause. Tool failures, missing search results, OAuth and execution handling also need to be separated out.
  • Next approach: capture the exact error and timestamp, test each integration independently, check model/provider health, and verify the produced code or report before calling a run successful. Avoid changing several settings at once.

30 October 2026 · Windows gateway startup investigation

Why is Hermes taking so long to start?

A focused investigation into Windows logon startup, the Hermes_Gateway scheduled task, the VBS launcher, Python process creation and gateway initialisation. Task Scheduler reported a successful action and the gateway was running when checked, but historical watchdog events show earlier startup and responsiveness problems. The root cause remains unconfirmed.

  • Windows task: Hermes_Gateway is enabled, triggers at logon, runs interactively as Administrator and launches the VBS gateway launcher. Its 30 October 09:07:56 run returned result 0; this does not prove gateway readiness.
  • Gateway: status showed PID 5672 listening on 127.0.0.1:8642, shared by the configured Hermes profiles.
  • Historical evidence: a 25 October startup watchdog timed out after 600 seconds while bundled skills synchronisation was in progress. Logs from 13–28 October also recorded event-loop liveness failures; the 28 October thread dump included conversation-context compression activity, which is a clue rather than a proven cause.
  • Windows diagnostics: Task Scheduler Operational logging was disabled, explaining why earlier event queries returned no history. It was enabled on 30 October for the next controlled startup capture.
  • Next test: after the next Windows logon, inspect Task Scheduler events for Hermes_Gateway before manually starting Hermes, then correlate those events with gateway status and process start time.

31 October 2026 · Plugin-import startup investigation

A targeted mitigation — but not yet a permanent fix

Startup logs captured plugin import timeouts and a watchdog exit. Thread stacks showed Firecrawl and Keenable imports while plugin discovery was waiting. The configured DDGS search and Exa extraction backends were checked and preserved; Firecrawl and Keenable were then disabled.

  • Evidence: the watchdog recorded a 300-second startup deadline and exit code 75. Firecrawl, Keenable and web-openai-native import timeouts were logged; Exa also registered late after a timeout.
  • After the targeted change: the gateway reached its running state, its health endpoint returned HTTP 200, Telegram and WhatsApp connected, the cron scheduler enumerated five profiles, and the user reported the terminal eventually loaded.
  • Separate issue: an invalid Nous Portal refresh token was reported for the auxiliary Nous client. It did not prevent the gateway health check from succeeding.
  • Assessment: plugin imports are a confirmed part of the observed delay path. Disabling Firecrawl and Keenable is a credible partial mitigation, but a clean Windows logon test is still outstanding. No permanent fix is claimed.

1 November 2026 · Dashboard launch delay and session-pruning failure

Dashboard eventually became usable after a long wait

The user launched hermes dashboard. The CLI reported that it was routing to the machine dashboard with the jhermes profile preselected, but the command appeared to wait without returning to the prompt. The dashboard eventually appeared and remained functional. The user estimates the wait at roughly five to ten minutes and will check the duration more accurately tomorrow.

  • Environment verified: Hermes Agent v0.22.5+2381.g0431192, Python 3.14.9, Git installation reported up to date. hermes status showed the gateway running via the default-profile multiplexer.
  • Dashboard/session display: the dashboard showed 841 total sessions, 841 active in store, 0 archived, 84,303 messages and 8 sources; a separate visible count showed 215. The full status command reported 7 active sessions. These may represent different measures and have not been reconciled.
  • Pruning: the dashboard displayed a failed old-session pruning operation. A 30-day retention period was discussed as a possible value, but the configured retention setting and exact pruning error have not been verified.
  • Command Prompt termination: the user terminated the Command Prompt that had been running hermes dashboard; the dashboard then became available and is still working. This is a sequence of events, not proof that terminating CMD caused recovery or that the Hermes gateway itself was crashed.
  • Jobs: hermes status reported 18 active jobs out of 20 total. No evidence yet links these jobs to the dashboard delay.
  • Assessment: this is a confirmed long dashboard-startup symptom and a reported pruning failure. Database locking, session-store size, scheduled jobs, plugins and dashboard initialisation remain hypotheses only. No plugin change, database deletion, reinstall or permanent fix was made during this investigation.
  • Next check: record the exact dashboard launch duration tomorrow; capture the complete pruning error and investigate session-store/database diagnostics before changing retention or deleting data.

Evidence labels

Verified: directly confirmed by command output or artifact. Observed: output seen, cause unknown. Suspected: plausible explanation needing a test. Unresolved: not diagnosed. Never describe a hypothesis as a verified fix.
