# Operations log — 1 November 2026

## Incident: Hermes dashboard takes several minutes to appear; old-session pruning fails

**Status:** Dashboard eventually working; startup delay and pruning failure unresolved.

**Objective:** Record the observed dashboard launch behaviour and CLI/session statistics without claiming an unproven cause or fix.

### 1. Environment and gateway checks

- Hermes Agent reported: `v0.22.5+2381.g0431192` (stable, local build `0431192d69d4`), installation method Git, reported up to date.
- Python: `3.14.9`.
- `hermes status` reported the gateway running via the default-profile multiplexer.
- Provider shown by status: `custom:freellmapi`.
- Scheduled jobs: 18 active, 20 total.
- `hermes status --full` reported 7 active sessions and last activity 4 minutes earlier.
- No credentials, API keys, private addresses or machine-specific secrets are included in this public log.

### 2. Dashboard launch sequence

- The user ran `hermes dashboard` from Command Prompt.
- CLI output: it was routing to the machine dashboard with profile `jhermes` preselected.
- The command appeared to remain waiting; no immediate browser/dashboard availability was observed.
- The user later terminated the Command Prompt that had been running the dashboard command. The dashboard then appeared and remained usable.
- The user estimates the total wait was approximately 5–10 minutes, but will check the timing more accurately tomorrow.

**Important distinction:** The observed action was terminating the Command Prompt running `hermes dashboard`. This does not establish that the Hermes gateway was terminated or that closing CMD caused the dashboard to recover. The gateway had been reported as running by `hermes status`.

### 3. Dashboard session/pruning display

The dashboard displayed:

| Metric | Displayed value |
|---|---:|
| Separate visible session count | 215 |
| Total sessions | 841 |
| Active in store | 841 |
| Archived | 0 |
| Messages | 84,303 |
| Sources | 8 |

The dashboard also displayed **“Failed to prune”** for the old-session pruning operation.

A 30-day retention period was discussed as a possible/example value, but the actual configured age threshold has not been confirmed. The exact underlying pruning error has not yet been captured.

The dashboard's 841 stored sessions and the 7 active sessions reported by `hermes status --full` may be different measures. They have not yet been reconciled.

### 4. What is verified, and what remains a hypothesis

**Verified from command output or user observation:**
- The gateway was reported running.
- Hermes version and Python version above.
- Dashboard command selected the `jhermes` profile.
- Dashboard eventually appeared and was still working at the time of the report.
- Dashboard displayed the session counts above and a pruning failure.
- Status reported 18 active scheduled jobs.

**Not established:**
- That plugins caused this particular dashboard delay.
- That scheduled jobs caused the delay.
- That the database is corrupt, locked or too large for this operation.
- That pruning is configured for 30 days.
- That terminating the dashboard Command Prompt caused recovery.
- That the gateway itself was crashed.

### 5. Safe next checks

1. Tomorrow, time the dashboard launch from command invocation until the dashboard is usable.
2. Capture the complete pruning error text and identify the configured retention threshold from the actual Hermes configuration/documentation.
3. Inspect supported database/session diagnostics and determine whether another Hermes process holds the store open.
4. Compare dashboard session counts with CLI status using the same definitions.
5. Investigate scheduled-job and plugin startup timing only with evidence.

**Preservation rule:** Do not manually delete session records, SQLite database/WAL files, disable additional plugins, change retention, or reinstall as part of this incident until the cause is better understood.
