# Operations log — 30 October 2026

## Incident: slow and unreliable Hermes Gateway startup on Windows

**Status:** Ongoing — root cause not confirmed.

**Objective:** establish why Hermes is not consistently ready after Windows logon, without applying speculative workarounds or changing several variables at once. The investigation focuses on the Windows scheduled task, VBS launcher, Python process creation and gateway initialisation.

### 1. Windows scheduled task

- **Verified:** the registered task is `Hermes_Gateway`; it exists and is enabled.
- **Configuration observed:** trigger is **At logon time**; logon mode is **Interactive only**; run-as account is `Administrator`.
- **Action observed:** `wscript.exe //B //Nologo` launches the `Hermes_Gateway.vbs` script under the Hermes gateway-service directory.
- **Task history:** last run shown as 30 October 2026 at 09:07:56, with last result `0`.
- **Interpretation:** result `0` means Windows reports the task action completed successfully. It does not prove Python completed gateway initialisation or that Hermes was ready for requests.

### 2. Gateway status and shared profiles

- **Verified at the time checked:** `hermes -p default gateway status` reported a running gateway process, PID `5672`, listening on `127.0.0.1:8642`.
- The listener was shared across the configured `coder`, `jhermes`, `local` and `tokenharbor-test` profiles.
- **Limitation:** this confirms the gateway was running when queried; it does not explain why it had not been ready earlier.

### 3. Launcher and Python environment

- The scheduled task calls `Hermes_Gateway.vbs`. The inspected script sets the Hermes home directory, Python environment variables and working directory, then starts the bundled Python `3.14.9` interpreter with `hermes_cli.main gateway run` in a hidden, detached process.
- The matching CMD launcher and dated backups were inspected. They contain some differences in Python launcher details.
- **No rollback or edit was made.** The Python update has not been established as the cause.

### 4. Historical startup and watchdog evidence

**25 October — startup watchdog timeout**

- The startup watchdog recorded a timeout after 600 seconds.
- The captured main-thread stack was in bundled skills synchronisation, including `tools/skills_sync.py` and the quiet bundled-skills sync called during gateway startup.
- **Interpretation:** skills synchronisation was in progress during that particular timeout. This does not prove it caused the later morning startup delays.

**13–28 October — event-loop liveness failures**

- Gateway logs contain repeated critical messages that the event loop missed three consecutive liveness probes and that the watchdog exited with code `75` so the service supervisor could restart it. Recorded dates include 13, 15, 17, 18 and 28 October.
- For 28 October, the main gateway log entry was at 19:06:16; the shutdown-watchdog log recorded the event at 19:06:17. Its thread dump included activity in conversation-context compression code.
- **Interpretation:** an event-loop responsiveness failure is confirmed for that occasion. Compression activity is a lead, not a proven root cause.

**30 October — multiple launch modes**

- The exit diagnostic log recorded a direct CLI launch at 09:17 with `detached:false`, followed by a detached gateway launch at 09:45 with `detached:true`.
- The log does not establish who initiated the first launch or why. It shows that more than one launch mode was used that morning, not that the scheduled task itself failed.
- The prior-session state database integrity check returned `ok`; a previous-session marker alone is not proof of a crash.

### 5. Windows Task Scheduler Operational logging

- **Discovery:** the `Microsoft-Windows-TaskScheduler/Operational` event log was disabled. This explains why the earlier event query returned no results: Windows was not recording those operational events.
- **Change made:** enabled the channel with the following command:

```powershell
wevtutil sl Microsoft-Windows-TaskScheduler/Operational /e:true
```

- This enables collection for the next test; it does not recover historical events from when the channel was disabled.

### 6. Next controlled test

At the next Windows logon, before manually starting Hermes:

1. Query the Task Scheduler Operational log for events relating to `Hermes_Gateway`.
2. Record whether Windows triggered the task, whether the action completed, and any reported error or return code.
3. Then run `hermes -p default gateway status`.
4. Correlate the Windows event timestamps with the gateway process start time and Hermes logs.
5. Only then decide whether the evidence points to task triggering, the VBS launcher, Python process creation or gateway initialisation.

Read-only event query used for the next test:

```powershell
wevtutil qe Microsoft-Windows-TaskScheduler/Operational /q:"*[EventData[Data='Hermes_Gateway']]" /rd:true /c:30 /f:text

hermes -p default gateway status
```

### 7. Changes deliberately not made

- No Hermes profiles were deleted or recreated.
- No Python installation was rolled back.
- No launcher files were edited or restored from backup.
- No scheduled jobs or messaging integrations were disabled.
- No timeouts were increased and no watchdogs were disabled.

This keeps the investigation evidence-led and avoids introducing new variables before the next startup capture.

## Current conclusion

The Windows task is configured to start Hermes at logon and the gateway can run. Historical Hermes logs also show a startup timeout and event-loop watchdog exits. Task Scheduler Operational logging was disabled, so the earlier Windows event query had no history; logging is now enabled for the next test.

**The root cause is not yet known.** The next Windows logon is the key test. Capturing Task Scheduler events before manually starting Hermes should help distinguish a task-trigger problem from a launcher, Python process-creation or gateway-initialisation delay.
