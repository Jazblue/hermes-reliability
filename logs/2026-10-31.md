# Operations log — 31 October 2026

## Incident: Hermes startup delay and plugin-import timeouts

**Status:** Partially improved; permanent resolution not yet verified.

**Objective:** record the new evidence from the 31 October startup investigation without presenting a successful gateway health check as proof that Windows startup is fixed.

### 1. What the logs showed

- Hermes Agent was running version `0.22.5`.
- The gateway startup watchdog reported that startup had exceeded 300 seconds. It later exited with code `75` because the gateway had not reached a live event loop within the watchdog deadline.
- Plugin loading recorded 10-second timeouts for `web-firecrawl`, `web-keenable` and `web-openai-native`.
- The log also recorded a late registration attempt from `web-exa` after its load had timed out.
- The captured thread stacks showed plugin worker threads importing Firecrawl and Keenable modules while the plugin-discovery thread was waiting for plugin loading to finish.
- This is direct evidence that plugin imports were involved in the delayed startup path. It does not establish why those imports were slow (for example, it does not prove antivirus, disk or Python is the cause).

### 2. Configuration checked before changing plugins

The profile configuration showed:

- Web search backend: `ddgs`.
- Extraction backend: `exa`.

Firecrawl and Keenable were not the configured search or extraction backends. This mattered because disabling a selected backend could have broken the corresponding web capability.

### 3. Targeted change made

The following bundled plugins were disabled using Hermes' plugin command:

- `web-firecrawl`
- `web-keenable`

The configured DDGS search backend and Exa extraction backend were deliberately preserved. No further web plugins were disabled in this step; the separate `web-openai-native` and `web-exa` timeout messages remain evidence to monitor, not a reason to make additional speculative changes.

### 4. Successful gateway checks after the change

Subsequent output provided these positive checks:

- The gateway reached its running state.
- The local health endpoint returned **HTTP 200 OK**, with status `ok` and Hermes Agent version `0.22.5`.
- Telegram connected.
- WhatsApp connected.
- The multiplexed cron scheduler started and enumerated all five configured profiles.
- The user reported that the Hermes terminal eventually loaded successfully.

These checks confirm that the gateway and several key services were operational during that run.

### 5. Separate authentication warning

The logs also reported that the auxiliary Nous Portal client could not authenticate because its refresh token was invalid (`invalid_grant`). This is a separate authentication issue. It did not prevent the gateway from reaching its running state or the health endpoint from returning HTTP 200. It remains unresolved and should be handled separately if the user needs that auxiliary Nous integration.

### 6. What this does — and does not — prove

**Supported conclusion:** slow or timed-out plugin imports were a real part of the observed startup failure path. Disabling the two plugins whose import stacks were captured was followed by a successful gateway run and successful health check. This is a credible partial mitigation.

**Not yet proven:**

- That disabling Firecrawl and Keenable alone caused the successful startup.
- That every remaining plugin import will complete reliably.
- That the Windows logon task will start Hermes reliably after a fresh reboot.
- That the Nous Portal authentication warning has been resolved.

No clean Windows reboot/logon verification was completed as part of this incident record. The user should not be asked to perform repeated restarts just to create evidence; the next natural restart can be used as the next controlled test.

### 7. Change control and preservation

- Existing Hermes profiles and scheduled jobs were preserved.
- DDGS and Exa configuration was retained.
- No Python reinstall, profile deletion, timeout increase or watchdog disablement was performed as part of this targeted plugin change.
- No credentials, tokens, private addresses or machine-specific paths are included in this public log.

## Current assessment

**Partial improvement, not a confirmed permanent fix.** The strongest finding is the plugin-import bottleneck evidenced by thread stacks and timeout messages. Disabling Firecrawl and Keenable was a targeted, reversible change, after which the gateway became healthy and the terminal eventually loaded. The next useful evidence is whether the system starts normally at the next ordinary Windows logon, and whether any remaining plugin timeouts recur.
